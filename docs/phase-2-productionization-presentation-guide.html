01 · Purpose

Turn research outputs into a controlled service

Phase 1 established dataset acquisition/approval, exploration, feature engineering, baseline models, DVC versioning, MLflow tracking, and initial evaluation. Phase 2 adds the controls and software needed to assess candidates, serve inference through a defined interface, package it, deliver it repeatably, observe it, and recover from failures.

Core presentation point: productionization mechanics are implemented; the current models are not approved for real institutional use. OULAD is retrospective evidence; synthetic data is development-only. The formal release decision is blocked pending prospective institutional evidence, approved thresholds/policy, fairness review, and an intervention policy.

Describe the system as a governed research demonstrator and production-oriented architecture. Do not claim a live production deployment without an actual approved rollout record.

Git tracks code/configuration; DVC tracks datasets and generated artifacts; MLflow tracks experiment runs, model artifacts, and registered versions. Prometheus/Grafana track operational metrics. This division connects a release to its inputs and checks without confusing registration with approval.

Candidate lifecycle

Reproduce → evaluate → assess quality and fairness → log/register with evidence tags → verify metadata and feature contract → retain as a candidate.

Serving lifecycle

Select an immutable numeric registry version or allowlisted catalog → verify tags, threshold, and fitted feature contract → load → become ready only after successful validation.

03 · Model testing and risk

Check report integrity and release suitability separately

The quality implementation validates both the contents of metrics reports and the evidence needed for a particular deployment claim. Structural pass does not imply model usefulness, fairness, calibration, or deployment eligibility.

Checks and rationale

  • Required fields, finite metrics, valid metric ranges, positive sample counts, and a non-empty 2×2 confusion matrix.
  • Nested day-30/60/90 evaluations are checked separately, preventing a valid aggregate from hiding a malformed cutoff.
  • Optional configured thresholds cover PR-AUC, balanced accuracy, operating-point recall, calibration error, and fairness. They must be justified by prevalence, support capacity, error costs, calibration needs, and institutional review; examples are not universal approvals.
  • Fairness reports include group sizes/label counts, selection rate, true-positive and false-positive rates, precision, accuracy, and Wilson confidence intervals. Default research comparisons require 30 observations and at least five positives and five negatives; under-sized groups remain visible but ineligible for gap calculation.

The canonical model_quality DVC stage writes linked assessments for full-course OULAD, OULAD early warning, and synthetic planner tracks. A completed assessment can truthfully be blocked and still be valid retained evidence.

Deployment eligibility: requires prospective institutional evidence and claim, configured intervention policy, and a passing formal fairness report with evaluable attributes. Current retrospective and synthetic tracks are intentionally ineligible.

Why: high accuracy alone can hide class imbalance, poor calibration, subgroup gaps, leakage, or harmful intervention choices. A report checker cannot detect every bias or prove that an intervention benefits students.

04 · Traceable model versions

MLflow registry lifecycle

Registered versions carry tags for quality/fairness/deployment gates, selection, evidence type and claim, operating threshold and source, feature-contract SHA-256, and feature count. Synthetic/early-warning versions also preserve development-only and cutoff details.

Registration writes tags, reads the stored version back, compares requested values, and assigns the candidate alias only after successful verification. A mismatch raises an error. The alias points reviewers at a candidate; it is not production approval. Production references immutable numeric versions rather than moving aliases.

Reproduction and audit

scripts/reproduce_all.ps1 runs DVC synthetic validation and model quality, then trains/registers full-course OULAD, OULAD day-30/60/90, and synthetic day-30/60/90 tracks. It requires local data and explicit MLflow URI/username/password environment variables. Output reports/models go in Git-ignored .repro/. The registry audit expects 4 full-course, 3 early-warning selected, and 12 synthetic comparison versions. It checks names, run associations, required tags, gate booleans, threshold range, positive feature count, and hash format. This is a metadata-consistency audit, not proof of efficacy or eligibility.

06 · Access and privacy

Protect the boundary around inference

  • Machine clients use X-API-Key; the key is never embedded in browser code.
  • Browser login uses a PBKDF2 password verifier and issues a signed, time-limited HttpOnly session cookie. Production uses Secure/SameSite settings and Origin checks for cookie-authenticated mutations.
  • Nginx serves React, applies security headers, and proxies API calls same-origin. Production API is not publicly exposed as a separate service.
  • Input validation rejects nested/non-finite values, unknown features, identifiers, outcomes, and post-outcome data. Student wellbeing is bounded numeric self-report, not clinical diagnosis.
  • Credentials are runtime secrets; MLflow tokens, API keys, session secrets, and plaintext passwords must not enter Git or image layers.
  • Serving images use non-root users; Compose app containers use read-only root filesystems and temporary writable mounts.

These controls do not replace institutional SSO, role/access lifecycle, audit policy, consent and retention review, or privacy governance.

07 · Repeatable packaging

Docker images and automated delivery

Separate API and React/Nginx images support Compose and Kubernetes. A combined Dockerfile.render packages Nginx and loopback-only FastAPI in one Render service for a protected research demonstration. Nginx proxies same-origin routes; an entrypoint validates config and supervises both processes. Render explicitly uses development mode and is not the production topology. Model/data artifacts are runtime inputs, not baked into the serving image.

GitHub Actions CI covers lint, PyTest, dependencies, DVC/notebook structure, synthetic smoke training, quality/fairness behavior, API inference smoke, deployment/monitoring config, and frontend checks/build. Licensed-data notebooks are structurally checked where raw inputs are absent, not claimed executed. The Docker workflow builds API, web, and Render images; main publishes latest and SHA tags. Release should use immutable SHA/digest.

Manual protected deployment validates full commit reachability, images/digests, model versions/tags, cluster permissions, creates private-pull and release-specific secrets, applies TLS/workload/network controls, waits for rollouts, verifies public HTTPS, and retains evidence. Recovery is separately guarded and captures before/after state.

Passing CI verifies the configured software checks for that run. It does not supply prospective student evidence, approve a model, or prove a deployment happened.
08 · Deployment targets

Different topologies for different purposes

Local Compose

Research/integration: API, web, Prometheus, Pushgateway, Alertmanager, Grafana. Management ports are localhost-bound. Grafana is mapped to host port 3001 due to a local port conflict.

Render

Single authenticated research demo, one combined image, same-origin gateway, generated API/session secrets, prompted login/MLflow values, readiness at /readyz. Free-tier memory/ephemeral storage can constrain model load. Monitoring stack is excluded.

Kubernetes

Production-oriented split API/web, HTTPS ingress, NetworkPolicy, replicas, probes, HPA, PodDisruptionBudget, private image pulls, release-specific configuration, and rollback. Requires institution-owned cluster, DNS/TLS, metrics server, network policy enforcement, secrets, and approved model.

Status language

Manifests and workflows are implemented mechanics. Do not call a service deployed unless the actual external workflow/resource evidence exists.

09 · Operate and recover

Prometheus, Grafana, alerts, rollback

Prometheus scrapes aggregate API request/latency metrics and Pushgateway; Grafana visualizes them; Alertmanager groups active alerts. Rules cover API availability, server-error rate, p95 latency, stale/missing batch heartbeat, and aggregate drift warnings. Batch metrics are opt-in; dashboards need pushed pipeline runs to show those results. Drift exports aggregate changes, not row-level student data or identifiers.

A scheduled HTTPS workflow separately checks liveness, readiness, threshold, and feature-contract metadata. Recovery pins image/model/configuration to release history, requires protected confirmation for mutation, captures evidence, and expects post-rollback readiness/model/alert review. External alert receivers, incident owner, independent retention, and a measured restore/RTO/RPO drill still require an institution.

12 · Presentation Q&A

Questions to be ready for

Why doesn't quality pass mean ready for deployment?

Structural checks validate report integrity. Eligibility additionally needs prospective evidence, fairness, and a reviewed intervention policy.

Why Git, DVC, and MLflow?

They track distinct things: code/config, datasets/generated artifacts, and experiments/model versions.

Why use a numeric registry version?

It is immutable and reproducible. An alias can move, so it is useful for candidate review but not as the production reference.

Why keep synthetic data?

To develop and exercise planner schemas, features, and software workflows; it cannot validate real students.

Has the system been deployed?

Answer only from actual deployment logs and resource evidence. Source code and workflow definitions alone are not a rollout.
