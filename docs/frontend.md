# React web application specification

## 1. Purpose and boundary

The React application in `frontend/` separates the student planning experience
from the operator model-testing experience. The default student view requests
only understandable planning information: a goal, subjects, tasks, deadlines,
availability, focus-cycle preferences, a small optional academic snapshot, and
optional numeric wellbeing context. It does not request names, student
identifiers, credentials, diagnoses, or free-text wellbeing records. A generated
plan remains decision support and requires human review.

## 2. Functional workflow

The interface provides two deliberately separated workflows:

1. **Student planner (default).** The student enters a structured goal, subjects,
   optional self-reported academic estimates, tasks, deadlines, availability,
   preferred session length, and break length. The browser sends these values to
   `/v1/student-study-plan`. The API selects the deployment default model,
   constructs its exact fitted feature vector, runs risk scoring internally, and
   combines the signal with task priority and real capacity. The response exposes
   the schedule, rationale, recommendations, and an understandable evidence
   summary; it does not expose model IDs, versions, hashes, thresholds, or column
   names.
2. **Admin / model testing.** An explicit operator mode loads `/v1/models` and
   `/v1/model-metadata`, permits selection from the deployment allowlist, renders
   the exact raw feature contract, and calls `/v1/risk-score`. This preserves the
   reproducible testing interface without presenting engineered columns to
   students.

The student feature adapter maps only semantically compatible values. For
example, an attendance estimate can populate an attendance percentage, but the
service does not invent LMS clicks, active days, verified assessment events, or
historical outcomes. Unavailable fields remain missing and are handled by the
fitted preprocessing pipeline. The response states that institutional data is
not connected and labels the support signal as provisional.

The administrator browser submits only a short allowlisted `model_id`; it never
submits a filesystem path, MLflow URI, threshold, or model artifact location.
Changing the selected test model clears prior raw inputs and results before
loading the new fitted contract.

## 3. Security design

The browser calls only the same-origin `/api` path. Nginx strips that prefix and
proxies the request to FastAPI. The service API key is reserved for monitoring
and machine clients and is never compiled into JavaScript.

Human login uses an environment-provisioned username and PBKDF2-SHA256 password
verifier. FastAPI issues a signed, time-limited cookie with `HttpOnly` and
`SameSite=Strict`; production also sets `Secure`. Cookie-authenticated POST
requests must have an approved same-origin `Origin` header. The gateway adds a
restrictive Content Security Policy, framing protection, MIME-sniffing
protection, a referrer policy, and a permissions policy. Kubernetes and Compose
run both containers with restricted privileges and read-only root filesystems.

This remains a single protected operator credential, not a university identity
and access-management system. The visual student/admin separation is not an
authorization boundary. Institutional production must integrate the gateway
with the approved SSO/OIDC provider, enforce student and administrator roles,
retain reviewed audit events, and manage account lifecycles before broad access.

## 4. Local development

Install and test the React application:

```powershell
cd frontend
npm ci
npm run check
npm test
npm run build
```

For live development, start FastAPI on port 8000 and run `npm run dev`. Vite
proxies `/api` to FastAPI. `CORS_ALLOWED_ORIGINS=http://localhost:5173` is also
supported for deliberate direct API calls, but the proxy is the normal browser
path.

For the integrated container path, use the repository-root Compose procedure in
`docs/deployment.md` and open `http://localhost:8080`.

## 5. Verification

The frontend test suite checks input coercion, risk-threshold interpretation,
protected-login rendering, the default student-friendly view, deferred metadata
loading, and the administrator model selector. TypeScript compilation is a required CI gate.
The production build is generated by Vite and copied into a non-root Nginx
image. `npm audit --audit-level=high` is also a CI gate; dependency findings
must be resolved or formally documented before release.

Browser tests do not establish model quality, real-world validity, fairness, or
intervention effectiveness. Those remain separate release gates described in
the model-risk and production-readiness documents.
